## 3. Процесс, подготовка и кеш

```text
prepare(schema + chat token lengths)
  → obtain_artifact(existing run, hashes)
  → evaluate_gate(raw outputs → score → old quality_gate)
  → publication(atomic accepted pointer + release journal)
```

Веса и тензоры не передаются между задачами: только URI, ID и SHA-256.
Реальная подготовка разбирает golden JSONL, проверяет ID/вход, строит chat tokens
точным токенизатором и сохраняет длины. Это реальная работа с данными, а не sleep.
JSON результата сохраняется на диск; Prefect persist_result сохраняет описание.

Ключ `release.cache_key`:
`SHA256(canonical({data_sha256: SHA256(file bytes), config}))`.
Config включает точную revision/hash токенизатора, template hash, max_length=4096,
хеш системной инструкции, hash lock-файла
и hash кода обработки. Имена файлов, mtime и порядок dict не определяют ключ.
У Prefect дополнительно есть namespace рабочего каталога, чтобы кешированный URI
не указывал в чужой workspace. Файлы результатов — `.state/prepared/`, описания
Prefect — `.state/prefect-results/`, локальная база — `.prefect/`. Все игнорируются.

| Опыт | Доказательство |
|---|---|
| Сбой STUB после подготовки | [flow-stub-failure.log](flow-stub-failure.log): Completed → injected failure, exit 1 |
| Новый процесс после сбоя | [flow-stub-recovery.log](flow-stub-recovery.log): Cached, дальнейшие стадии Completed, exit 0 |
| Повтор успешного flow | [flow-stub-repeat.log](flow-stub-repeat.log): Cached; одно событие выпуска |
| Другие байты по прежнему пути | [flow-stub-invalidation.log](flow-stub-invalidation.log): PREPARED, Completed |
| Настоящий input, сбой | [flow-real-failure.log](flow-real-failure.log): токенизация завершена; управляемый exit 1 |
| Настоящий input, восстановление | [flow-real-recovery-rejection.log](flow-real-recovery-rejection.log): Cached → gate False → exit 1 |
| Настоящий input, изменённые байты | [flow-real-invalidation.log](flow-real-invalidation.log): повторная подготовка Completed; старый eval закрывает выпуск |

В последнем опыте к строкам добавлены пробелы: путь сохранён, байты изменились,
кеш инвалидирован. Старые source hashes больше не подходят, поэтому выпуск
отклонён до допуска. Исходные байты восстановлены в finally;
[сверка восстановления](real-invalidation.json). Никакие train-данные не менялись,
причины повторно обучать модель нет. Даже при логически тех же JSON проверка
исходных байтов специально остаётся строгой.

Автоматических retry нет для неверной схемы, несовместимого артефакта и отказа
качества. Сетевое получение вынесено в отдельную команду и может быть повторено
ограниченно оператором. Журнал попыток отличается от события выпуска: каждый
процесс получает новый attempt_id, тот же выпуск сохраняет release_id.

## 4. Контракт и безопасная публикация

Manifest фиксирует ID/URI, точную базу, список файлов и их SHA-256, tokenizer,
chat template, generation, dtype/device, protocol/golden и исходные отчёты.
`model_sha256` — SHA-256 канонического словаря relative_path → file hash.
Перед публикацией и перед загрузкой API хешируются **фактические файлы**.

`provenance.py` сверяет исходные source hashes, восстанавливает прежний protocol hash,
заново считает score по сырым ответам и вызывает неизменённую
`hw67/evaluation/solution.py::quality_gate`. Не только читает старое поле passed.
Связанный [release-report.json](../release-report.json) создан программно, содержит
исходный evaluation_run_id, training_run_id, метрики, hashes и False с причиной.
Разные канонизации учтены явно: исторический fingerprint ДЗ6+7 использует JSON с
пробелами; новый runtime использует канонический JSON без пробелов.

`validate_release` требует int schema_version=1, непустые строки, lowercase SHA-256,
полный runtime с пересчётом хеша, status=complete, **passed is True**, непустой eval ID,
совпадающие ID/хеши. Метрики — конечные int/float в [0,1], bool/строки запрещены.
Missing, чужой отчёт, NaN/Inf и stale runtime закрывают выпуск.
Отдельные тесты проверяют порчу файла после создания manifest.

Указатель записывается во временный файл **рядом** с целью, затем flush/fsync и
os.replace. При отказе качества запись даже не начинается; при ошибке replace
старые байты сохраняются, tmp удаляется. Ошибки диска внесены mock, диск не заполнялся.

Для одного писателя выбран небольшой write-ahead intent `pending.json`:

1. Проверить gate и реальные файлы; сохранить intent с manifest/report/release_id.
2. Атомарно обновить accepted.json.
3. Дополнить журнал только при отсутствии release_id; атомарно заменить JSONL snapshot.
4. Удалить intent.

После сбоя между 2 и 3 повтор восстанавливает событие; после 3 повтор не дублирует его.
Иной выпуск сначала восстанавливает pending предыдущего. release_id зависит от
manifest **и всего связанного решения**, включая runtime и evaluation_run_id.
Согласованность после разрыва доказана [crash](flow-stub-pointer-crash.log),
[recovery](flow-stub-pointer-recovery.log), [repeat](flow-stub-pointer-repeat.log).
[flow-evidence.json](flow-evidence.json) содержит два события для двух разных
решений и все попытки. Повтор того же решения нового события не добавляет.
Это не распределённая транзакция и не многописательский реестр.

[real-rejection.json](real-rejection.json) фиксирует одинаковый SHA-256 accepted
до/после реального отказа:
`7e3c483870116f11444f230ece989bd08deda7c5099d5ba2ecd315e7b3ae802c`.
Это локальный accepted pointer, не операция назначения MLflow alias champion.

Серия опытов использует один локальный Prefect API server, но каждый flow запускается
в новом независимом процессе. Это устраняет повторный старт orchestration API
перед каждым коротким опытом. Изначальный startup timeout до создания flow сохранён
в [prefect-startup-timeout.log](prefect-startup-timeout.log); он не считается
доказательством отказа gate. Прямой запуск flow допускает 90 секунд на startup.

## 6. API и фактически загруженная версия

FastAPI lifespan запускает фоновую загрузку, проверку файлов и прогрев. Пока они
не завершились, health=200, ready=503, generate=503. Ошибка загрузки оставляет
ready=503. Успешный ready возникает только после backend.warmup().

[Реальный HTTP smoke](real-api.json) фиксирует 200/503 во время загрузки, затем
ready=200, неправильный лимит → 422 при calls 0→0 и настоящий ответ модели:

```json
{"answer":"{\"answer\":\"A\"}","output_tokens":6,
 "model_id":"Qwen3-0.6B-base-c1899de289a0",
 "runtime_sha256":"b6d7d52993cd9e4aa2660d59904892dea88bb5793883d50deda2561b6771636f"}
```

request_id и длительности сохранены в полном JSON. Лимит ровно 16, как в eval;
сервис не разрешает клиенту произвольно менять generation. Тело ≤64 KiB, prompt
1..16000 символов и ≤4096 chat tokens. Схема и токенный лимит проверяются до generate.
Lock допускает одно вычисление одновременно, остальные запросы ждут.

model_id/runtime_sha256 ответа берутся из **backend в памяти**. Опыт A → B → A
со STUB реализован в `test_http_loaded_version_restart_and_rollback`: после
публикации B ответ и ID старого процесса остаются A; после перезапуска — B;
управляемая публикация ранее принятой A + перезапуск возвращает A.
Это проверка управления версиями, не второй реальный допущенный адаптер.

Для настоящей модели отдельный новый процесс повторно загрузил текущий manifest,
прогрелся и выдал тот же ID/hash: [real-restart.json](real-restart.json).
После реального PASS сценарий обновления такой же: публикация согласованного
manifest, остановка старого API, запуск нового, проверка ready и loaded ID.
Откат — публикация сохранённого ранее допущенного manifest с исходным отчётом,
затем перезапуск; gate не обходится. Для текущего baseline bootstrap retention
отдельно документирован, он не притворяется успешной публикацией кандидата.

## 7. Измерение 8+8 запросов

Прогрев завершён до начала. Первые восемь одинаковых golden prompts выполняются
при c=1 и c=2, max_new_tokens=16, greedy decoding. На каждый ответ фактически
получено 6 токенов. [Все 16 попыток](requests.jsonl),
[JSON](benchmark.json), [CSV](benchmark.csv), [stdout](benchmark.log).
Ошибки/таймауты не удаляются; в этом прогоне их нет.

| c | n | Успехи | Ошибки | Весь пакет, с | Успешных/с | Средняя успешная, с | Макс. успешная, с | Задержки ошибок |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| 1 | 8 | 8 | 0 | 22,579 | 0,354 | 2,822 | 3,178 | нет наблюдений |
| 2 | 8 | 8 | 0 | 22,411 | 0,357 | 5,250 | 5,809 | нет наблюдений |

Среднее измеренное вычисление: c=1 2,819 с, c=2 2,801 с. Среднее ожидание до
вычисления: 0,00017 с и 2,445 с. Клиентская задержка при c=2 почти удвоилась из-за
очереди перед одним compute slot, тогда как requests/s почти не изменились.
Таймер поколения включает токенную проверку и синхронный generate; queue_seconds
отсчитывается до получения слота. Клиент дополнительно измеряет HTTP и сериализацию.
Значения сняты одним процессом на CPU и маленькой выборкой, устойчивый p95 не оценён.

Prefill обрабатывает входные токены и создаёт KV-cache. Decode последовательно
предсказывает следующие токены, используя накопленные K/V. Память KV растёт с
числом слоёв, KV heads, длиной контекста, dtype и числом одновременных последовательностей.
Здесь нет continuous batching: последовательный Transformers-сервис не доказывает
скорость SGLang/vLLM. Возвращается цельный JSON, измерена полная задержка; TTFT/ITL
не измерялись и не оценивались по косвенным данным.

## 8. Доступ, ограничения и сдача

Все команды — в [README](../README.md). В Git нет весов, .venv, Prefect SQLite,
кешей и Docker volumes. Для baseline преподаватель может скачать публичную базу
ровно по revision и выполнить `scripts/restore_base.py`; исходные eval уже в Git,
DVC private remote для чтения готовой сдачи не нужен. Отвергнутый адаптер находится
в существующем локальном MLflow volume. Для передачи его преподавателю нужен
отдельный согласованный канал; публичная ссылка не создана и не заявляется.

Работа рассчитана на localhost и одного писателя, без многопроцессного inference,
внешней аутентификации и потоковой генерации. Для Prefect CLI на Python 3.12
явно закреплён importlib-metadata; SQLAlchemy закреплён на 2.0.43. Первоначальные
неудачи запуска оркестратора не считаются отказом gate: итоговые журналы отдельно
показывают создание flow, состояние задачи допуска и сохранность указателя.

Остаётся запись и приложение одного видео по [сценарию](video.md).
